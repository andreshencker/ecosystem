# 09 — QA — Proceso de Calidad

**Versión:** 1.0 | **Fecha:** 2026-07-06 | **Estado:** Oficial

---

## Propósito

El QA Agent garantiza que cada pieza de software entregada funciona correctamente, cumple los criterios de aceptación definidos, y no regresiona funcionalidades existentes.

> Nada se mergea sin el sign-off del QA Agent. Sin excepciones.

---

## Responsabilidades del QA Agent

1. Revisar cada PR cuando el agente reporta COMPLETION al CTO
2. Verificar que los tests existen y pasan
3. Verificar que los criterios de aceptación de la Task están cumplidos
4. Detectar regresiones en funcionalidades previas
5. Reportar el resultado al CTO Agent

**El QA Agent NO:**
- Implementa código de producción
- Diseña la arquitectura de tests
- Aprueba merges (eso es el CTO)

---

## Proceso de QA

```
CTO Agent → QA Agent: "Revisar PR de TASK-{ID}"
                │
                ▼
    QA Agent lee los criterios de aceptación de la Task
                │
                ▼
    QA Agent revisa el PR:
      ├── ¿Los tests existen?
      ├── ¿Los tests pasan?
      ├── ¿Los criterios de aceptación están cubiertos?
      ├── ¿Hay regresiones en tests anteriores?
      └── ¿El comportamiento del código coincide con la especificación?
                │
                ▼
    QA Agent reporta QA_RESULT al CTO
      ├── APPROVED → CTO hace code review
      └── CHANGES_REQUESTED → CTO informa al agente
```

## Niveles de testing

### Nivel 1 — Unit Tests (obligatorio para todo dominio)

Testean la lógica de negocio de cada service en aislamiento. Los mocks se usan para dependencias externas (Communications Platform, Google Calendar API), pero NO para la base de datos.

```typescript
// CORRECTO — testa el comportamiento, no la implementación
it('should reject WorkEvent confirmation when endTime is before startTime', async () => {
  const workEvent = createWorkEvent({ startTime: '22:00', endTime: '20:00' });
  await expect(workEventService.confirm(workEvent.id)).rejects.toThrow(
    'WorkEvent end time must be after start time'
  );
});

// INCORRECTO — testa la implementación interna
it('should call workEventRepository.save() once', () => { ... });
```

**Coverage mínimo:** 80% de branches en services de dominio.

---

### Nivel 2 — Integration Tests (obligatorio para todos los endpoints)

Testean los endpoints completos contra una base de datos real de test. Verifican el flujo completo desde el controller hasta la respuesta.

```typescript
// Siempre usa DB real de test — nunca mock de repositorio
describe('POST /work-events/:id/confirm', () => {
  it('returns 200 and WorkEvent in confirmed state', async () => {
    const { token, businessId } = await createTestBusiness();
    const workEvent = await createTestWorkEvent(businessId, { status: 'draft' });
    
    const response = await request(app)
      .post(`/work-events/${workEvent.id}/confirm`)
      .set('Authorization', `Bearer ${token}`)
      .expect(200);
    
    expect(response.body.status).toBe('confirmed');
    expect(response.body.rateResult).toBeDefined();
  });
});
```

---

### Nivel 3 — E2E Tests (obligatorio para flujos críticos)

Testean el flujo completo a través de múltiples dominios. Por ejemplo, el flujo desde WorkEvent confirmado hasta Revenue Domain.

```typescript
// Verifica el flujo cross-domain
it('should create RevenueLine in RevenueDraft after WorkEvent confirmation', async () => {
  const { token, businessId } = await createTestBusiness();
  const customer = await createTestCustomer(businessId);
  const contract = await createTestContract(businessId, customer.id);
  const workEvent = await createTestWorkEvent(businessId, { contractId: contract.id });
  
  // Confirma el WorkEvent
  await workEventService.confirm(workEvent.id);
  
  // Verifica que el evento se procesó en Revenue
  await waitForEvent('WorkEventConfirmed');
  
  const draft = await revenueDraftRepository.findByContract(contract.id);
  expect(draft.lines).toHaveLength(1);
  expect(draft.lines[0].workEventId).toBe(workEvent.id);
});
```

## La regla de los mocks

```
MOCKS PERMITIDOS:
  ✅ Communications Platform API (no queremos enviar emails reales en tests)
  ✅ Google Calendar API (no queremos hacer llamadas reales)
  ✅ Stripe / Payment processors (no queremos procesar pagos reales)
  ✅ Servicios externos en general

MOCKS PROHIBIDOS:
  ❌ Base de datos (MongoDB) — siempre real en tests de integración
  ❌ Redis — siempre real en tests de integración
  ❌ Event Bus — siempre real en tests E2E
  ❌ Servicios internos del ERP entre sí
```

**Razón:** Los mocks de DB y Event Bus son la causa más común de que tests pasen localmente pero fallen en producción.

## Checklist de QA

```
TESTS
  [ ] Los tests unitarios están escritos y pasan
  [ ] Los tests de integración están escritos y pasan
  [ ] Si hay flujo cross-domain: tests E2E existen y pasan
  [ ] No hay tests skippeados sin justificación
  [ ] No hay regresiones en tests existentes (todos pasan)
  [ ] Coverage mínimo del 80% en services de dominio

CRITERIOS DE ACEPTACIÓN
  [ ] Cada criterio de aceptación de la Task tiene al menos un test que lo cubre
  [ ] Los criterios se verifican desde la perspectiva del usuario/negocio, no del código

COMPORTAMIENTO
  [ ] El endpoint retorna el status code correcto para el happy path
  [ ] El endpoint retorna error apropiado para inputs inválidos
  [ ] El businessId en las respuestas pertenece al Business del JWT
  [ ] Los eventos publicados tienen el payload correcto

SEGURIDAD
  [ ] El endpoint sin JWT retorna 401
  [ ] El endpoint con JWT de otro Business no retorna datos del Business actual
  [ ] No hay campos sensibles en respuestas que no deberían estar

DOCUMENTACIÓN
  [ ] La documentación en docs/ refleja el comportamiento implementado
```

## Resultado de QA: CHANGES_REQUESTED

Cuando QA no aprueba, el reporte incluye:

```
QA_RESULT: CHANGES_REQUESTED
taskId: S04-T003

FAILURES:
  1. [TEST] Test "should reject when endTime <= startTime" falla con:
     Expected: throw ValidationException
     Received: 200 OK (workEvent created without validation)
     File: src/work/work-event.service.ts:line 45

  2. [CRITERIA] Criterio "GET /work-events filtra por businessId" no está testeado
     La implementación parece correcta pero no hay test que lo verifique.

  3. [REGRESSION] Test S03-T002 falla después de este cambio:
     describe('Calendar sync') → 'should not import duplicate events'
     Parece que el cambio en el WorkEvent schema afectó algo en Calendar.

RECOMENDACIÓN:
  Corregir los tres puntos antes de solicitar nuevo review.
  El punto 3 (regresión) es el más crítico y requiere investigación.
```

## Definition of Done desde la perspectiva de QA

Un PR está LISTO para el CTO review cuando:

1. **Tests pasan:** `npm test` retorna 0 errores
2. **Coverage:** la métrica de coverage no decreció vs la rama principal
3. **No regresiones:** ningún test que pasaba antes ahora falla
4. **Criterios cubiertos:** cada criterio de aceptación tiene evidencia de test
5. **Comportamiento verificado:** QA ha ejecutado manualmente el flujo crítico al menos una vez (o tiene un test E2E que lo hace)
