# DEC-019 — Notification Trigger Flow — Complete Architecture Reference

> **Purpose of this document**
> Every notification generated by the Communication Platform — whether triggered by a business service, a platform administrator, or an external application — follows exactly the same pipeline. There is only one notification engine. This document is the canonical reference for any developer who needs to understand, integrate with, or extend the notification system.

---

## 1. Purpose

The Communication Platform must serve three categories of notification triggers:

1. **Internal company triggers** — raised by business logic running inside the platform for a specific company (user invitation, password reset, welcome email, etc.)
2. **Internal platform triggers** — raised by platform-level operations that concern the platform itself (admin invitation, platform security alerts, etc.)
3. **External application triggers** — raised by third-party systems connected to a company via integration tokens (ERP, CRM, HR system, e-commerce platform, trading app, mobile app, etc.)

All three of these converge into a **single, shared notification engine**:

```
NotificationService.notifyEvent(payload)
```

This function is the **only** permitted entry point for any notification in the platform. Business services, platform services, and external endpoint handlers all resolve to this single call. The engine does not know — and must not care — whether the trigger was internal or external.

## 2. Notification Sources

### A — Platform Admin

The Platform Admin area generates notifications for platform-level operations. These use the **platform company configuration** (credentials, theme, layout).

| Event | Canonical Key | Trigger |
|---|---|---|
| Platform Admin invitation | `security.platform_admin_invitation` | `POST /users/invite` (platform_admin → platform_admin) |
| Platform Admin password reset | `security.platform_forgot_password` | `POST /auth/forgot-password` (global scope) |
| Platform Admin password changed | `security.platform_password_changed` | `PATCH /users/me/password` (global scope) |

### B — Company (Owner / Admin / Operator)

Company-scoped business actions generate notifications using that **company's own configuration** (its credentials, theme, and layout templates).

| Event | Canonical Key | Trigger |
|---|---|---|
| Email verification | `security.company_verify_email` | `POST /auth/register` (public registration only) |
| User invitation (all roles) | `security.company_user_invitation` | `POST /users/invite`, `POST /companies/with-owner` |
| Forgot password | `security.company_forgot_password` | `POST /auth/forgot-password` (company scope) |
| Password changed | `security.company_password_changed` | `PATCH /users/me/password`, `POST /auth/reset-password` (company scope) |
| Welcome message | `security.company_welcome_message` | **Optional — business-triggered only; not part of auth flow** |

> **`security.company_user_invitation` is the single invitation event for ALL invited users**, regardless of role. It is triggered both by `POST /users/invite` (for company_admin, operator, viewer) and by `POST /companies/with-owner` (for company_owner). The `data.role` variable in the payload allows the template to address the invitee by their specific role.

### C — External Applications

Third-party systems connected to a company via an integration token. The token **identifies the company automatically** — the external app never sends a `companyId`.

| Type of system | Example events |
|---|---|
| ERP | `orders.order_confirmed`, `billing.invoice_issued` |
| CRM | `crm.lead_assigned`, `crm.deal_closed` |
| HR platform | `hr.employee_onboarded`, `hr.payslip_ready` |
| E-commerce | `store.order_shipped`, `store.return_initiated` |
| Trading platform | `trading.trade_executed`, `trading.margin_call` |
| Mobile app | `app.otp_requested`, `app.session_alert` |

All three source types call the same `NotificationService.notifyEvent()`. Nothing else changes downstream.

### Component descriptions

| Component | Role |
|---|---|
| **NotificationService** | The single entry point. Orchestrates resolve → compose → deliver → log. |
| **EventCatalogue** | Stores the event template per domain per company: subject, HTML content, required/optional variables, file attachments. |
| **DomainCatalogue** | Maps a `domainKey` to the channels configured for that company and their credential references. |
| **ProviderCredentials** | Stores encrypted credentials for the configured provider (SMTP, SendGrid, Twilio, S3, etc.). Never returned in plaintext. |
| **Layout Renderer** | Composes the final HTML by injecting event content into the company layout template with company and theme context. |
| **Provider Adapter** | Sends the rendered notification through the configured transport. Isolated — email adapters never know about SMS, and vice versa. |
| **ExecutionLog** | Records the complete result of the notification attempt: channel, provider, success, error, timestamps. |

## 4. Internal Company Owner / Admin Flow

When a business action occurs inside the platform for a company, the owning service already holds `companyId` in its execution context.

```
  Company Owner creates a new user
           │
           ▼
  UsersService.createInvitedUser()
    → creates user record
    → knows: actor.companyId
           │
           ▼
  await notificationService.notifyEvent({
    companyId:  actor.companyId,
    event:      'security.company_user_invitation',
    email:      invitee.email,
    payload: {
      data: {
        firstName:    invitee.firstName,
        companyName:  company.displayName,
        role:         invitee.role,
        email:        invitee.email,
        tempPassword: generated,       // plaintext — in-memory only, never stored
        loginUrl:     config.loginUrl,
      }
    }
  })
           │
           ▼
  NotificationService resolves:
    - EventCatalogue  →  email template for 'company_user_invitation'
    - DomainCatalogue →  company's email channel + credential ID
    - ProviderCredentials → decrypted SMTP / SendGrid config
    - Theme + Layout  →  company's branded HTML wrapper
           │
           ▼
  Email delivered via company's provider
           │
           ▼
  ExecutionLog recorded
```

**Key point:** The business service contributes only `companyId`, `event`, `email`, and `payload`. It has zero knowledge of templates, credentials, providers, or rendering.

## 5. Internal Platform Admin Flow

Platform Admin operations use the **platform company** configuration. The platform company holds Grapifly's own credentials and layout. All platform-level notifications (admin invitations, security alerts) are delivered through these credentials.

```
  Platform Admin invites another admin
           │
           ▼
  UsersService.createInvitedUser()
    → creates platform_admin user
    → uses: config.PLATFORM_COMPANY_ID
           │
           ▼
  await notificationService.notifyEvent({
    companyId:  config.PLATFORM_COMPANY_ID,   ← not the actor's company
    event:      'security.platform_admin_invitation',
    email:      invitee.email,
    payload:    { data: { firstName, tempPassword, loginUrl } }
  })
           │
           ▼
  NotificationService resolves platform company assets
    (platform credentials, platform layout, platform theme)
           │
           ▼
  Email delivered via Grapifly credentials
           │
           ▼
  ExecutionLog recorded
```

**Key point:** The code path is identical to company notifications. The only difference is `companyId = PLATFORM_COMPANY_ID`.

## 6. External Application Flow

External systems — ERP, CRM, mobile apps, trading platforms — trigger company notifications by calling an HTTP endpoint with an integration token. The server resolves `companyId` from the token; the external app never knows or sends a company identifier.

```
  External App (e.g. ERP)
           │
           │  POST /notifications/event
           │  x-integration-token: gpf_live_a1b2c3d4...
           │  {
           │    "event": "orders.order_confirmed",
           │    "email": "customer@company.com",
           │    "payload": { "data": { "orderId": "ORD-123" } }
           │  }
           ▼
  Endpoint handler
           │
           ▼
  IntegrationTokenResolver.resolveByToken(rawToken)
    → SHA-256(rawToken) → find CompanyIntegration
    → assert isActive === true
    → assert not expired
    → update lastUsedAt
    → return { companyId, integrationKey, environment }
           │
           ▼
  await notificationService.notifyEvent({
    companyId,   ← resolved from token, NOT from request body
    event:  'orders.order_confirmed',
    email:  'customer@company.com',
    payload: { data: { orderId: 'ORD-123' } }
  })
           │
           ▼
  NotificationService resolves that company's assets
    (credentials, layout, theme, event template)
           │
           ▼
  Notification rendered and delivered
           │
           ▼
  ExecutionLog recorded
```

**Key point:** The external app never sends `companyId`. It is always resolved server-side from the integration token. Cross-company triggering is structurally impossible.

## 7. Credential Resolution Rules

All notification delivery uses the credentials of the **resolved company** — not the caller's company, not the platform company, and not a global fallback.

```
  Trigger source                 Resolved companyId          Credentials used
  ─────────────────────────────────────────────────────────────────────────────
  Company Owner / Admin          actor.companyId             Company's own
  Company Operator               actor.companyId             Company's own
  Platform Admin (company scope) actor.companyId             Company's own
  Platform Admin (admin scope)   PLATFORM_COMPANY_ID         Platform credentials
  External App                   token → CompanyIntegration  That company's own
```

### Golden credential rule

> **Notifications always use the credentials associated with the resolved `companyId`.**
> There are no shared credentials. There is no global fallback. No company can send through another company's provider.

## 8. Golden Rules

These rules are **non-negotiable**. Any code that violates them is non-compliant with this decision.

```
  ✓  Never send emails directly from a business service.
     Business services call notifyEvent() — nothing else.

  ✓  Never send SMS directly from a business service.

  ✓  Never render HTML templates inside a business service.
     Rendering is the exclusive responsibility of the Layout Renderer.

  ✓  Never bypass NotificationService.
     There is no legitimate reason to call a provider adapter directly
     from application code.

  ✓  Every notification must originate from an EventCatalogue event.
     Ad-hoc email bodies in code are prohibited.

  ✓  External apps never send companyId.
     The integration token is the only permitted source of company identity
     for external callers.

  ✓  NotificationService does not know whether the trigger was internal
     or external. It receives a canonical payload — that is all.

  ✓  Credential decryption happens only inside the provider adapter.
     No other layer ever sees decrypted secrets.

  ✓  ExecutionLog is always written, regardless of delivery success or failure.
     Failed deliveries must be observable.
```

## 9. Developer Integration Guide

This section shows exactly how to trigger a notification from application code. There is **one pattern and one pattern only**.

### Pattern

```typescript
// Inside any business service that needs to trigger a notification:

async function someBusinessAction(actor: AuthContext, data: ActionData): Promise<void> {
  // 1. Perform the business operation
  const result = await this.someRepository.create(data);

  // 2. Trigger the notification — this is the ONLY permitted integration pattern
  await this.notificationService.notifyEvent({
    companyId: actor.companyId,                    // resolved from auth context
    event:     'security.company_user_invitation', // canonical: domainKey.eventKey
    email:     data.recipientEmail,
    payload: {
      data: {
        firstName:    data.firstName,
        companyName:  company.displayName,         // from company record
        role:         data.role,                   // assigned role
        email:        data.recipientEmail,
        tempPassword: generatedPassword,           // plaintext — in-memory only
        loginUrl:     this.config.get('APP_BASE_URL') + '/auth/login',
      },
    },
  });
}
```

### Rules for callers

| Rule | Explanation |
|---|---|
| Always use `domainKey.eventKey` format | `'security.company_user_invitation'`, not `'user_invitation'` |
| Never construct HTML | Put the template in EventCatalogue. The caller provides `payload.data.*` variables only. |
| `companyId` comes from context | Auth context for internal calls. Resolved by `IntegrationTokenResolver` for external calls. |
| Do not catch NotificationService errors silently | Log them. A failed notification must produce an observable error. |
| Do not add a notification-specific try/catch to silence failures | Let the execution log capture the result. Business logic should not be aware of delivery failures. |

### Finding the right event key

1. Open the **Domains** page → find the domain for the action (e.g. `security`, `orders`, `billing`).
2. Open **Events** → filter by domain.
3. Use `domainKey.eventKey` as the `event` parameter.
4. Check `requiredVariables` in the event to know which `payload.data.*` fields you must provide.

## 10. Responsibilities

| Component | Responsibility |
|---|---|
| **Business Service** | Knows when an event occurred. Knows `companyId` from its own context. Calls `notifyEvent()` with the canonical payload. Knows nothing about templates, credentials, or channels. |
| **External App Endpoint** | Validates the integration token. Calls `IntegrationTokenResolver`. Builds the canonical payload with resolved `companyId`. Calls `notifyEvent()`. |
| **CompanyIntegration** | Maps an integration token to `{ companyId, integrationKey, environment }`. Validates active + expiry. Updates `lastUsedAt`. Never exposes secrets. |
| **NotificationService** | Orchestrates the full pipeline: resolve event → resolve domain → resolve credentials → compose → deliver → log. Accepts the canonical payload and nothing more. |
| **EventCatalogue** | Stores the notification template per domain per company: subject, HTML content, required/optional variables, required/optional file keys. The source of truth for what a notification looks like. |
| **DomainCatalogue** | Stores which channels are active for a domain and which credential record each channel uses. |
| **ProviderCredentials** | Stores encrypted channel credentials. Decrypted only at the moment of delivery, only inside the provider adapter. Never returned in any API response. |
| **Layout Renderer** | Injects event content into the company's layout HTML. Applies theme tokens (`primaryColor`, `fontFamily`, etc.) and company context (`supportEmail`, `logoUrl`, etc.). Produces the final HTML. |
| **Provider Adapter** | Sends the rendered content through the configured transport (SMTP, SendGrid API, Twilio REST, S3 PUT, etc.). Isolated per channel. Email adapters do not know about SMS. |
| **ExecutionLog** | Records every delivery attempt: channel, provider, `success`, `error`, `renderedAt`, `deliveredAt`. The primary source for observability and audit. |

## 11. Future Extensions

Because business services call only `notifyEvent()` with a canonical payload, new delivery channels can be added **without modifying any business service**.

```
  Future channel additions require only:

  ├── New ChannelKey in schema  (e.g. 'push', 'whatsapp', 'slack', 'teams', 'webhook')
  ├── New ProviderAdapter       (implements the channel interface)
  ├── New DomainCatalogue entry (company enables the channel for a domain)
  └── New EventCatalogue entry  (company configures the template for the channel)

  Zero changes to:
  ├── Business services
  ├── Platform Admin services
  ├── External app endpoint handlers
  └── NotificationService interface
```

Planned future channels:

| Channel | Notes |
|---|---|
| Push Notifications | iOS / Android via FCM or APNS |
| WhatsApp | via WhatsApp Business API |
| Slack | via Incoming Webhook or Bot API |
| Microsoft Teams | via Adaptive Cards / Webhooks |
| Webhooks | HTTP POST to external systems |

When any of these is implemented, existing callers automatically gain access to the new channel by updating their EventCatalogue and DomainCatalogue configuration. No code changes in business services.
